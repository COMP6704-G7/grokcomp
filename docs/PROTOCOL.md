# 本地实验协议

本协议依据附件计划及私有组库 `COMP6704-G7/grokcomp` 的 `93b2248e351d4bb9e4dda8ac32a6999b8970404b` 实现。计划中的 baseline 权重衰减和预算原本待组内确认；本次执行采用 λA=1、λLion=5、100000 步上限，作为本地冻结的比较配置，仍需组内确认才能替代统一基线。

## 数据与模型

- 数据为 x·y mod 97，x∈[0,96]、y∈[1,96]，共 9312 条。
- 输入 [x, op, y, eq]，预测结果 token。词表 99；保留原仓库输出头的 99 类交叉熵，包括两个特殊 token。
- 两层、宽度128、四头、FFN宽度512的因果 Transformer；沿用原仓库 Block，包括其 LayerNorm / residual 顺序。模型源码从原 `main.py` 提取到共享模块，原入口重新导入同一实现。
- 每个 seed 先在 CPU 初始化模型，再使用同一全局 RNG 的 randperm 做 4656/4656 划分，与原脚本的 RNG 消耗顺序一致。不同 seed 的划分允许不同，同 seed 两种优化器的划分和初始权重完全一致。各运行保存索引及 SHA-256。
- 训练顺序使用独立的 CPU generator（seed+1000000）产生每个 epoch 的置乱；两种方法共享同 seed 的取样规则。原脚本是直接重排 train_data，新入口不承诺其逐步 batch 顺序与旧脚本一致。
- 每 epoch 共10个 batch：前9个512、最后一个48。没有丢弃或重复尾部样本。

## 更新与评估

- FP32，TF32关闭，不使用 AMP、编译、梯度裁剪或梯度滤波。
- 两种方法都对全部参数使用解耦权重衰减。AdamW foreach=False，epsilon=1e−8。
- 沿用原 LambdaLR 的10步线性 warmup；第一个更新的 lr=0，随后逐步升到设定峰值，之后恒定。日志同时保存当前 ηλ。
- 第0步仅用于初始化诊断；每100步在**同一份当前模型权重**上，以 eval 模式重新评估完整训练集和验证集。评估 batch=512。
- 主要阈值 val95；补充阈值 val99；train99 用于泛化延迟。三个指标都要求连续3次评估达标，记录该连续段起点；第0步不参与达标计数。
- 共同停止条件为 val99 连续3次达标（停止于第三次确认），或到100000步。主要结果同时保留 val95；不能将 val95 当作提前停止规则。
- ΔT=Tval99−Ttrain99，保留负值。未达标字段为 null，表格展示“>100000”；不把预算步数填入成功样本的均值。

## 学习率选择与正式比较

- seed0上跑三个 Lion 候选，每个同预算，λ固定5。
- 预先规定排序：val99达标优先 → Tval99较小 → Tval95较小 → 最终val准确率较高 → 较低lr。
- 三个结果完成后写入 frozen_selection.json；正式实验使用该lr及新seed1/2/3，禁止根据正式结果重选。
- 私有库目前只有原 Grokfast 训练代码和占位结果，没有可以复用且满足本协议的组内 AdamW 日志，因此本地补跑三个 AdamW 对照。
- AdamW采用固定组内起点，不做与Lion等量的搜索；报告应明确这一调参预算限制。若组内要求比较“等量调参后的最优结果”，需另开同预算的 AdamW 三候选筛选，不能修改当前结果定义。
- 本轮只做计划中的主任务，不额外展开weight decay分析。

### 等次数调参补充分析

首次固定基线比较后，为补齐调参预算公平性，增加 `scripts/matched_budget.py`：AdamW候选为5e−4、1e−3、2e−3，每档使用seed0、100000步上限、同一停止和选择规则，与Lion的三次筛选匹配。该网格是在首次正式结果可见后设定，应作为补充探索性证据，不能称为事前注册的确认实验。正式seed不参与候选排序。

补充结果位于 `results/matched_budget_study`。Lion原始日志、配置、初始权重、划分和源文件哈希通过相对目录符号链接原样复用，不新增Lion运行。AdamW筛选后冻结 `selected_adamw_lr`；若与原始基线不同，在seed1/2/3补跑选中值。公共协议中的 `adamw_lr`保留最初的名义参照值；各运行顶层 `lr`和补充冻结文件记录实际使用值。

两种方法都得到3次候选和相同每次预算上限，但实际步数与GPU时间因达标停止而不同。补充比较仍不声称全局最优，也没有联合搜索weight decay。报告和展示保留首次固定基线结果，另列此补充，不覆盖原始结果或隐去设计顺序。

## 计时、显存与断点

- 使用同一张 A100 GPU0，所有候选和正式运行串行，不在该GPU上并行启动本实验。
- 记录实际CUDA同步后的时间。训练每步耗时覆盖取样、前向、反向、优化器、调度器及同步；完整集合评估单列，不混入该平均值。
- wall time从初始化完成后开始，包含第0步诊断评估、完整集合评估、日志和运行内检查点开销；不包含环境安装和模型构建。
- 达标 wall time对应连续达标段的第一个检查点，当时尚未完成连续性确认；confirmed_step另行记录。两种方法采用同一约定。
- 显存统计为 max_memory_allocated，包括评估和训练；另统计 optimizer state 实际持久张量字节。不要把总峰值与优化器状态内存混为一谈。
- 每5000步保存模型、优化器、调度器、RNG、取样置乱与游标、指标及累计时间。结束后保存最终状态。
- 异常时保留最后一个已完成检查点，丢弃之后的未提交训练；续跑重写日志，避免重复行。计时不含离线停机，segments记录启动段数。若正式运行续跑，应注明其计时限制，必要时另做计时重跑。
- metadata记录硬件、PyTorch/CUDA版本、父git revision及实际实验源文件哈希，避免把未提交代码误认为原始仓库版本。

## 验收

1. `python -m pytest -q` 验证官方等价、原模型和划分、阈值与续跑。
2. 独立pilot各1000步检查损失、准确率、时间和显存，不参与正式汇总。
3. 三次tuning完成后冻结；六次formal组成三个成对比较。
4. 分析工具校验成对初始权重、划分、协议及运行环境，生成三张PNG/PDF图、逐次CSV、汇总CSV/JSON与结果说明。
5. 报告与展示引用这些真实产物；没有完成的结果明确保留为空，不用模拟数据替代。

## 第二轮诊断与结论修订

原入口的实际默认参数是Adam/weight_decay=0；AdamW/1来自其代码注释，并非已确认的CLI基线。初版把待统一配置当成本地正式起点，不能据此宣称原基线复现已完成。原脚本保持训练循环不改，seed0复跑50000步，最终val=87.84%，未达95%；这显示延迟泛化，但没有完全复现README的达标步数。

控制诊断固定seed0和模型、划分、取样规则、学习率（AdamW=1e-3、Lion=2e-4），扫描AdamW decay=1/0.1/0.01/0，Lion取5倍，以匹配峰值ηλ。每次10000步且关闭提前停止。该诊断揭示衰减对泛化速度影响显著，不能把高衰减下快速达标当作原零衰减任务的特性。

此外，六个原始正式检查点保持全部参数和RNG/取样状态继续到10000步；检查原日志前缀逐行相同，核对源文件、模型初值、划分和环境一致。AdamW三个seed首次确认后都曾跌破95%，Lion三个均保持≥99%。旧首次达标统计仍成立，但不足以推出稳定泛化的排名。

新增“观察期内持续99%起点”：从该检查点到10000步所有观测都≥99%，且至少有三个观测。它是明确标注的回顾性诊断，不替代原预定指标，不保证预算以后稳定。该起点平均Lion=1566.7步、AdamW=7100步。续跑的wall time有两段，这里不重新比较稳定达标的wall-time速度；补充搜索选中的AdamW/2e-3组未在此项中延长。

详细结果在 `results/diagnostics/DIAGNOSIS.md` 与 `results/diagnostics/formal_stability/STABILITY.md`。Lion核心与新入口未改，旧入口仅指定Lion时beta2自动采用0.99，其余旧优化器仍默认0.98；明确传入的beta2保持用户指定值。独立核查未发现标签泄漏、训练验证重叠或保存准确率错误。
